if (document.layers): the web forks in two

Two lines of code you typed more often than your own phone number, and the fork in the web they stood for.

var ns4 = document.layers ? 1 : 0;
var ie4 = document.all ? 1 : 0;

If you wrote JavaScript between 1997 and 2001, those two lines were probably the first thing in your script file, the way #include <stdio.h> opens a C program. Everything after them was a fork. Every menu, ticker and sliding panel got written once per browser, and then you crossed your fingers for the browsers you hadn't tested.

The odd part is that both lines were true of the same web. The same HTML, served from the same server, gave Netscape Navigator 4 one model of a page and Internet Explorer 4 another. Neither was a bug or a hack. Each was a serious answer to the same question, what if a page could change after it loaded?, and the answers were incompatible. Following how that happened explains more about how the web platform works than most specs do.

Before the fork: a frozen page

Brendan Eich wrote JavaScript at Netscape in about ten days in May 1995. It was code-named Mocha, appeared in the Navigator 2 betas as LiveScript, and became JavaScript in December 1995, when Netscape and Sun jointly announced it. The name was a marketing decision, which is why a language with almost nothing in common with Java has been explaining itself for three decades. Microsoft answered with its own implementation, JScript, in Internet Explorer 3 in 1996.

What the language could touch was small: the window, the document, forms and their fields, links, and from Navigator 3 in 1996, images. That last item mattered more than it sounds. Once document.images let you swap an image's src, you had the rollover, and the rollover was the first proof that a page could respond to a mouse. This vocabulary is sometimes called DOM Level 0. It was never a standard of its own. It was whatever Netscape shipped first and everyone else copied. (For a short while Microsoft was the one reverse-engineering Netscape, which is worth remembering when the story turns.)

Everything on that list shared one limit: the page itself was frozen. You could validate a form, open a window, swap a picture, and write text into the document while it was loading with document.write. Once loading finished, the layout was set. If you wanted different content, you asked the server for a different page.

What Dynamic HTML promised

In 1997 both vendors broke that rule. Netscape Communicator 4 arrived mid-year and Internet Explorer 4 that fall, each carrying a bundle the marketing departments called Dynamic HTML. The pitch was three technologies stacked: HTML for content, CSS for style, and JavaScript to change either one while the visitor watched.

The piece that made it feel like a different medium was CSS positioning. You could write position: absolute; left: 120px; top: 40px and put a box exactly where you wanted it, on top of other boxes, with a z-index. A positioned box could be hidden, shown, moved or restacked, and doing that on a timer gave you animation. Menus that flew out. Panels that slid. Text that followed the cursor around, which was, to be fair, an entire genre for about two years.

Both browsers could do all of it. They disagreed, completely, about what the page was.

Two models of a page

Here is the core difference, stated as plainly as I can, because the rest of the mess follows from it.

Internet Explorer 4 made the entire document a live object. Every element, whether heading, paragraph, list item or table cell, was reachable through document.all, and you could change almost any of them after load: style, text, contents. The page reflowed around the change. Microsoft even added innerHTML, so you could replace an element's contents with a string of markup. (Hold that thought. It comes back at the end.)

Netscape 4 made a handful of special rectangles live. Only elements you had positioned, with CSS or with Netscape's own <layer> tag, showed up in document.layers. Everything else was, as far as script was concerned, set in concrete. You could move a layer, but you couldn't make the paragraph below it reflow, and you couldn't change a font size on the fly.

One browser exposed the whole page. The other exposed a few windows cut into it. That gap shows up in the smallest everyday jobs. To replace the text in a news box, Internet Explorer needed one line:

document.all["news"].innerHTML = "<b>Updated!</b>";

In Netscape 4, every layer owned a whole separate document, so to change a layer's contents you reopened that document and rewrote it:

var lyr = document.layers["news"];
lyr.document.open();
lyr.document.write("<b>Updated!</b>");
lyr.document.close();

Because each layer had its own document, reaching anything inside one meant walking down through it. An arrow image inside a menu layer was this in Netscape:

document.layers["menu"].document.images["arrow"].src
  = "down.gif";

and in Internet Explorer was simply document.images["arrow"].src. This is why Dreamweaver's generated MM_findObj helper is a recursive function that digs through each layer's document looking for a name. It was a way to find an image when the answer depended on where in the layer tree it happened to live.

My best guess at the root cause is the engine underneath. Navigator 4's layout engine formatted a page once, as the HTML streamed in, and wasn't built to go back and re-lay-out. Layers were a clever way to get movable regions without that, because each layer was laid out on its own. Internet Explorer 4 shipped with a new engine designed to re-lay-out the document when something changed, so it could expose everything. Same goal, different foundations, and the foundations decided what was possible.

Events ran in opposite directions

Then there were events. Click a link inside a div inside the body: who hears about it first? Internet Explorer said the link, then the div, then the body, with the event bubbling outward. Netscape 4 said the reverse. The event was captured at the window, document or layer on its way down, and you had to ask for it explicitly with captureEvents. The event also reached your code differently: Netscape passed it to your handler as an argument, while Internet Explorer kept it in a global, window.event. And the coordinates were measured from different places.

// Netscape 4
document.captureEvents(Event.MOUSEDOWN);
document.onmousedown = function (e) {
  x = e.pageX;
};

// Internet Explorer 4
document.onmousedown = function () {
  x = event.clientX;
};

pageX counted from the top-left of the document. clientX counted from the top-left of the visible window. Scroll the page and your drag-and-drop code was off by exactly the scroll distance, in one browser only, which is the kind of bug that survives three rounds of testing.

The eventual standard, DOM Level 2 Events in 2000, did something I find a little beautiful: it gave both camps their way. An event travels down in a capture phase, reaches its target, then bubbles back up, and you choose which phase you listen in. That is the third argument to addEventListener that most people leave at its default without ever knowing what it was for.

Why they diverged

Three forces pulled the models apart, and the third is the one people forget.

The market. The browser war was a fight for the desktop, and a proprietary feature was a weapon. Microsoft built Internet Explorer into Windows 98 in mid-1998, and the US Justice Department sued that same year with the bundling at the center of the case. Netscape, which had owned the market in 1995 and 1996, was losing share and shipping on a schedule its rival set. Nobody in that position waits for a committee.

The standard lagged the products. The W3C's DOM Level 1 became a Recommendation in October 1998, a full year after DHTML shipped, and it covered documents and elements but said nothing about events. The W3C had also gone with CSS positioning, so Netscape's <layer> tag never became a standard at all. For most of 1997 to 2000 there was no standard to follow even if you wanted to.

Netscape lost its footing. In 1998 Netscape released its source code, and that October the Mozilla project scrapped the old Communicator code to rebuild the browser around a new layout engine, Gecko. Rewrites take time, and Netscape 6 did not ship until late 2000. For roughly three years Netscape 4 and its point releases were the current Netscape. Joel Spolsky's 2000 essay Things You Should Never Do, Part I became famous for arguing that starting over is the worst strategic mistake a software company can make. Whether it was a mistake is still argued. What isn't in dispute is what it did to developers: it froze Netscape 4 as the version you had to support.

That last point is the one I'd underline. A bad browser that's about to be replaced is a short-lived problem. A bad browser that stays the newest version of its line for three years turns into a design constraint, and design constraints get built into everything.

How everyone coped

The first draft of everyone's code looked like the naive version: test for each browser, write the effect three times.

function showMenu(id) {
  if (document.getElementById) {
    document.getElementById(id)
      .style.visibility = "visible";
  } else if (document.all) {
    document.all[id]
      .style.visibility = "visible";
  } else if (document.layers) {
    document.layers[id].visibility = "show";
  }
}

Notice "show" against "visible". Even the values disagreed. After typing that branch for the fortieth time, people did the obvious thing and wrote it once:

function getObj(id) {
  if (document.getElementById)
    return document.getElementById(id);
  if (document.all) return document.all[id];
  if (document.layers) return document.layers[id];
  return null;
}

function getStyle(id) {
  var o = getObj(id);
  return o && o.style ? o.style : o;
}

function show(id) {
  getStyle(id).visibility =
    document.layers ? "show" : "visible";
}

That small trick, where a Netscape layer is its own style object and an Internet Explorer element has a .style, was in a thousand script files. It is also the seed of every JavaScript library you have used since. More on that in a moment.

There was a whole supply chain around the problem. Macromedia released Dreamweaver in December 1997, and a big part of its appeal was Behaviors: pick one from a menu and it generated the cross-browser JavaScript for you, MM_ prefix and all. Danny Goodman's Dynamic HTML: The Definitive Reference from O'Reilly in 1998 was the book on everyone's desk. Sites like Dynamic Drive handed out copy-and-paste menus and scrollers. CSS had its own trick: Netscape 4 didn't understand @import, so you put the good styles there and let it see only a plain stylesheet.

Some people gave up and picked a side. "Best viewed with Netscape Navigator" and "Best viewed with Internet Explorer" buttons, usually 88 by 31 pixels, were the heraldry of the era. And in 1998, a group of developers formed the Web Standards Project to lobby browser makers to support the W3C's specs. Developers organizing to pressure vendors was new, and it worked slowly, and then it worked.

How it ended

Internet Explorer 5, in March 1999, supported most of DOM Level 1, including document.getElementById. Netscape 6, built on Gecko, arrived in November 2000, supported the same call and dropped document.layers entirely. Netscape 4 faded slowly, and plenty of sites kept their three-way branch into the early 2000s because a customer on an old machine is still a customer.

The habit of sniffing for a browser by name died less by decree than by arithmetic. Look at the user agent string Internet Explorer sent:

Mozilla/4.0 (compatible; MSIE 5.0; Windows 98)

It introduces itself as Mozilla, Netscape's code name, and the usual telling is that servers sent the good page only to Mozilla, so everyone else started claiming to be it. The disguise never came off: every major browser today still opens its user agent string with Mozilla/5.0. Then more browsers showed up: Opera, which let its users choose which browser it claimed to be, then Mozilla, Konqueror, and Safari in 2003. Every new identity broke every script that asked who are you?. The scripts that asked can you do this? kept working. Peter-Paul Koch's QuirksMode, which became the field guide to these differences, argued for exactly that. The practice became known as object detection, and later as feature detection.

How sticky was the old habit? jQuery shipped a browser-sniffing helper, $.browser, deprecated it in 2009, and still didn't remove it until jQuery 1.9 in 2013.

What it left behind

The winner wrote the standard. Remember innerHTML? It was a Microsoft invention in Internet Explorer 4. It was in no part of DOM Level 1, 2 or 3. It became part of a web standard only in the HTML5 era, when the specs finally wrote down what every browser already did, by which point it was how half the web updated itself. XMLHttpRequest took the same road, starting life as an Internet Explorer 5 ActiveX object. The lesson I take from both is that standards are often a record of what survived, and the fight over who gets to be the thing that survives happens in the wild, in production, on your client's site.

The wrapper is the seed of the library. Look back at getObj. By 2005 Prototype's $() was getElementById in a shorter coat, and a year later jQuery generalized the idea into a whole way of working. The pattern keeps recurring: when the platform diverges, somebody writes the adapter once, everyone borrows it, and the divergence quietly moves from your code into a dependency. That isn't a bad outcome, but it explains why the pain of this era produced the tools of the next one.

It repeats. Vendor prefixes, -webkit- and -moz- and -ms-, were the same fork in CSS about a decade later. Mobile sites that worked only in WebKit were the same fork again. Each time it looks like a failure of the process. I'd argue it is the process: someone ships first, developers build on it, and the standard catches up to whatever turned out to matter. The only thing you control is how much of your code depends on the guess.

The end of the war had a cost too. Once Internet Explorer had won, plenty of teams stopped testing anywhere else, and Internet Explorer 6 shipped in 2001 and stayed the current version for roughly five years. It took the web about a decade to fully climb out of what "just support Internet Explorer" turned into. A monoculture is simpler for the person writing the code and worse for the thing they're building on. Most browsers today, Microsoft's included, run on one engine family, so the question isn't only historical.

The line that never died

Go back to the two lines at the top. ns4 and ie4 carry a hidden assumption: that the web has two browsers. Every sniffing script was a prediction about the future of the platform, and each prediction expired the next time the market moved.

One of the two lines got a strange afterlife. So many pages kept if (document.all) as their test for Internet Explorer that when other browsers later added document.all for compatibility, they had to make it lie. Open a console today and try it:

typeof document.all  // "undefined"
!!document.all       // false
document.all.length  // a number

The collection is there and it works, but it reports itself as undefined and tests as false, so that sniffing code written in 1998 takes the standards branch. The JavaScript specification carries a special case that exists for this one object. document.layers is simply gone.

The takeaway

If you keep one thing from the layers-versus-all years, I'd make it this: the web has never been designed first and built second. It gets built, argued over in production, and then written down. Netscape and Microsoft each shipped a guess in 1997. Developers paid for the disagreement for about four years, twice over in every script. What came out the other side was the DOM you use today, an events model that kept both designs, and a handful of Microsoft inventions that the standards adopted after the fact.

The habit it left behind is the more useful inheritance. Asking a browser who it is turned out to be a bet on a market that kept changing. Asking what it can do, as in if ('IntersectionObserver' in window), has held up for twenty-five years because it makes no prediction at all. The two lines at the top of this essay asked the wrong question millions of times, and the platform still carries a special case to keep them harmless. I can't think of a better argument for writing the check the other way.
