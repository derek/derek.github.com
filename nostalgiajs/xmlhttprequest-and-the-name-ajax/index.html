XMLHttpRequest: six years waiting for a name

The most important line of JavaScript of the 2000s shipped in 1999 with a name its own author calls an excuse, and then sat largely ignored for six years until somebody gave the technique around it a better one.

var req = new ActiveXObject(
  "Microsoft.XMLHTTP");

That is how you asked a server for something without leaving the page, in Internet Explorer 5, in March 1999. It isn't JavaScript's doing, strictly. ActiveXObject was Microsoft's way of letting script load a Windows component, the same door that opened Excel or the file system, and "Microsoft.XMLHTTP" was a component that happened to speak HTTP. The object it handed back could open a URL, send a request and give you the response as text. The page stayed where it was.

Every web application you use now is built on that ability. What I find worth an essay is the gap. The capability was in the dominant browser from 1999. The word "Ajax" arrived on February 18, 2005. In between, the object sat in the most widely used browser on earth and drew very little notice. The story of those six years is a story about a team with a deadline, a browser plug-in system, a recession and, in the end, a consultant who needed a shorter word for a client meeting.

Before: one click, one page

The web's original contract was simple. You clicked, the browser threw away the page, the server built a new one, and you waited. Jesse James Garrett, in the essay this story ends with, put the cost in one line: "While the server is doing its thing, what's the user doing? That's right, waiting."

Dynamic HTML, which arrived in 1997 and which split the web in two for a while, let a page change itself after it loaded. It did not let a page fetch anything new. Script could rearrange what the server had already sent, and that was all. If you wanted to check whether a username was taken, you submitted the form.

People found ways around this, and they were all smuggling operations. Anything with a src could carry a message to the server, so the standard trick was a frame the visitor couldn't see:

<iframe name="rpc" width="0" height="0"></iframe>

<script>
function checkName(name) {
  frames["rpc"].location =
    "check.asp?name=" + escape(name);
}
function gotResult(taken) {
  alert(taken ? "Taken" : "Available");
}
</script>

The server answered with a tiny HTML page whose only content was a script calling parent.gotResult(true). The response was, in effect, a function call sent as a web page. That is the Internet Explorer form; other browsers needed other hidden elements for the same trick. It failed in ways that were hard to see, because a hidden frame has no error handler and no status code you can read.

Microsoft had an official product in this space too. Brent Ashley's Remote Scripting page, which Ashley has kept online "for historical purposes", describes Microsoft Remote Scripting as solving the problem "by embedding a Java applet in the page to communicate with the server". A Java applet, to send a string. Ashley wrote a JavaScript-only alternative called JSRS "in the summer of 2000", built on hidden DHTML elements, and a second one called RSLite that passed its data in cookies. When people are carrying data in cookies on purpose, the platform is missing a feature.

A weekend in Redmond

The feature came from a mail team. Alex Hopmann, who worked on Exchange 2000 at Microsoft, wrote the history down in The Story of XMLHTTP, and it is the best primary source on any of this, so I'll lean on it.

Exchange needed a new Outlook Web Access, the webmail front end for corporate email. Hopmann dates the start to "probably sometime in late 1998". Two versions got underway: one of plain HTML pages, and one built with DHTML by Jim Van Eaton and Bob Gering. Of the first demo of the DHTML one, Hopmann writes, "I was just blown away". The DHTML one had a plumbing problem, though. In Hopmann's words, "they were basically doing hacky form-posts back to the server". So:

That weekend I startup up Visual Studio and whipped up the first version of what would become XMLHTTP. The first version didn't have async support hooked up and was pretty crude…

A component on one developer's machine doesn't help a product whose whole pitch is that you can walk up to any computer and read your mail. It had to be in the browser already. Internet Explorer 5 was, by Hopmann's account, "just weeks away from beta 2", its last beta. Another developer, Shawn Bracewell, rewrote the code to production quality and added the asynchronous mode and error handling. Hopmann, meanwhile, went looking for something that already shipped with Internet Explorer and could carry a stowaway. That turned out to be MSXML, Microsoft's XML parser library, whose team was run by Jean Paoli.

Which brings us to the name. I'd assumed for years that it was called XMLHTTP because it was designed to fetch XML. Hopmann says otherwise:

…the thing is mostly about HTTP and doesn't have any specific tie to XML other than that was the easiest excuse for shipping it so I needed to cram XML into the name (plus- XML was the hot technology at the time and it seemed like some good marketing for the component).

Two other lines from that account deserve to be better known. On security: "We did a quick security review but at the time no one really understood the seriousness or types of vulnerabilities that anything shipping could cause." And on quality: "no one other than OWA is going to try to call it so if it has a bug in the beta, worst case we just can't use it." The feature that would carry Gmail, Google Suggest and much of what got called Web 2.0 was checked in a week before a beta, on the theory that only one team would ever call it.

Internet Explorer 5 shipped in March 1999. Exchange 2000 and its Outlook Web Access followed, per Hopmann, "another year and a half" later. By then the piece it needed was on a great many desktops.

How the object worked

The API that went out in 1999 is, with small changes, the one in your browser today. A full request, as you'd have written it for Internet Explorer 5 or 6:

var req = new ActiveXObject("Microsoft.XMLHTTP");
req.onreadystatechange = function () {
  if (req.readyState == 4) {
    if (req.status == 200) {
      document.all["news"].innerHTML =
        req.responseText;
    }
  }
};
req.open("GET", "news.asp", true);
req.send(null);

Three things in there shaped a decade of code. The third argument to open is the async flag, and true meant your script carried on while the request was out. That one boolean is the A in Ajax. The callback fired on every state change, so everyone learned to test for the magic number 4; the W3C's first draft listed the states by name, and 4 was "Loaded". And the response came back two ways: as a string in responseText, or parsed into a document in responseXML if the server sent XML. Most people, most of the time, wanted the string.

Other browsers had no ActiveX, so they couldn't copy the component. They copied its interface instead and exposed it as a plain constructor, new XMLHttpRequest(), with Microsoft's method names and a spelling that capitalizes half an acronym. (Microsoft's own component was XMLHTTP, all capitals.) Wikipedia's history puts it in Mozilla's Gecko engine by 2002, in Safari 1.2 in 2004 and in Opera 8.0 in 2005. Aaron Swartz, looking back in A Brief History of Ajax, summed up those years: "Mozilla quickly followed suit and, while nobody I know used it, the function stayed there, just waiting to be taken advantage of."

Why it sat unused

Six years is a long time for a feature this useful to sit unused. I count four reasons, and I think they mattered in roughly this order.

It lived behind ActiveX. For the first few years the object existed in one browser on one operating system, behind the same mechanism that security-minded administrators were busy switching off. A public site that depended on it was betting on the visitor's browser and the visitor's IT department. Garrett, asked in a 2006 interview about the standards work then starting, said something that fits: people had tried to solve the problem "in proprietary ways for years", and the approach "didn't get traction until it was broadly available in a vendor-neutral way". The dates fit. Safari's support came in 2004, the year Gmail launched.

The timing was terrible. The object shipped in 1999 and the dot-com crash followed. Swartz's history has a bleak phrase for the period: "Shortly thereafter the bubble burst and web development crashed." The teams that might have spent 2001 building ambitious browser applications were mostly not employed to do so. Hopmann, explaining why the idea hadn't caught on even earlier, grants the slow connections and slow machines of the late 1990s ("typical machines were 200mhz") and then names what he thinks mattered most: developers don't make sweeping shifts quickly, and "these things take 3-5 years".

Nobody could see the examples. Outlook Web Access was the first big application built this way, and it lived behind corporate logins. Oddpost, a webmail service that opened in 2002 and behaved like a desktop mail client, charged a subscription, and Swartz reckons that is why it "didn't receive as much attention". Gmail launched on April 1, 2004, two and a half years after work on it began. Paul Buchheit recalls that along the way quite a few colleagues wanted it killed, or rebuilt with native client software, "not this crazy Javascript stuff". It was free, but its script was hard to follow. The breakthrough was the small one. Google Suggest appeared in December 2004, a search box that completed your query as you typed, and Hopmann notes that people "looked at the source code of that page to figure out how it worked". View Source was the school, and for once the lesson was short enough to read. Google Maps followed on February 8, 2005.

It had no name. Developers called it XMLHTTP, or remote scripting, or described it by pointing at Gmail. None of those fits on a slide. I think this reason is underrated, and the next section is my argument for it.

February 18, 2005

Ten days after Google Maps appeared, Jesse James Garrett of the San Francisco consultancy Adaptive Path published Ajax: A New Approach to Web Applications. Garrett was a user experience designer writing for other designers, and the essay reads that way. It has two diagrams and no code. The key sentences:

Google Suggest and Google Maps are two examples of a new approach to web applications that we at Adaptive Path have been calling Ajax. The name is shorthand for Asynchronous JavaScript + XML, and it represents a fundamental shift in what's possible on the Web.

Garrett was careful to say what the word covered: "Ajax isn't a technology. It's really several technologies", listed as XHTML and CSS, the DOM, XML and XSLT, XMLHttpRequest, and JavaScript "binding everything together". The essay claimed no invention. A follow-up Q&A three weeks later answered the obvious challenge directly: "Neither Adaptive Path nor Google invented Ajax." Asked why the thing needed a name at all, Garrett gave the most honest answer in the history of technical branding:

I needed something shorter than "Asynchronous JavaScript+CSS+DOM+XMLHttpRequest" to use when discussing this approach with clients.

In the 2006 interview Garrett filled in the scene. The technical people at a client already understood the pieces; the word was for "the business people I was dealing with". Then Garrett published the essay and "left the country", spending two weeks in Japan without internet access and coming home to "this avalanche of e-mail".

The speed of what followed is the evidence that the name was the missing part. On March 22, 2005, thirty-two days after the essay, Rails 0.11.0 shipped with the word in its release title and "Ajax helpers" as the headline feature. By the time Hopmann wrote his account, the term had reached the Wall Street Journal. Douglas Crockford, never one to oversell a trend, later described the moment this way: "In 2005, the idea of Dynamic HTML gained new energy and acceptance when it was renamed as Ajax."

Hopmann's verdict on his former employer is harsher than anything I'd write: "At Microsoft we totally blew the opportunity to evangelize and get out in front of this approach back in 1999."

Living with two constructors

Once everyone wanted to make requests, everyone needed the same few lines at the top of the file, because there were two ways to get the object. The canonical version is short enough that the Internet Explorer team published it themselves in January 2006:

if (window.XMLHttpRequest){
  // If IE7, Mozilla, Safari, etc: Use native object
  var xmlHttp = new XMLHttpRequest()
}
else
{
  if (window.ActiveXObject){
    // ...otherwise, use the ActiveX control for IE5.x and IE6
    var xmlHttp = new ActiveXObject("Microsoft.XMLHTTP");
  }
}

Read the first comment again. That post, by program manager Sunava Dutta, was announcing that Internet Explorer 7 would support "a scriptable native version of XMLHTTP", so that organizations which had disabled ActiveX could still run these applications. Microsoft was adopting the other browsers' imitation of Microsoft's own component, and putting itself on the "native object" branch of a test that had existed only to route around it. Internet Explorer 7 shipped in October 2006. The else branch stayed in libraries for years, since Internet Explorer 6 did too.

Careful versions of that snippet grew a ladder of try blocks, asking for "Msxml2.XMLHTTP" first and falling back to "Microsoft.XMLHTTP", because the component had been reissued under more than one name. Nobody wanted to write that twice, so the wrapper became the first thing every library offered. Prototype, the library that grew up alongside Rails, reduced a request to:

new Ajax.Request('/some_url', {
  method:'get',
  onSuccess: function(transport) {
    var response = transport.responseText || "no response text";
    alert("Success! \n\n" + response);
  },
  onFailure: function() { alert('Something went wrong...'); }
});

No readyState, no magic 4, no ActiveX. jQuery later did the same with $.ajax, and I'd guess a large share of working developers went a decade without typing XMLHttpRequest at all. The word in the method name was Garrett's.

The X went quietly. Garrett's own Q&A had already conceded that you didn't need XML, and could use "a technology like JavaScript Object Notation". Parsing a responseXML document with DOM calls was miserable next to getting an object you could use directly, and by December 2006 Crockford could tell an XML conference, to its face, that "JSON has become the X in Ajax".

What it left behind

A standard written by transcription. The W3C published its first working draft of "The XMLHttpRequest Object" on April 5, 2006, seven years after the object shipped. Its stated method was to "document a minimum set of interoperable features based on existing implementations", and it adds that "only features that are already implemented are considered". It also acknowledges being derived from the WHATWG's work documenting existing behavior. So the chain runs: a Microsoft team writes a component for its own product, other browsers reverse-engineer the interface, a group of browser people writes down what the copies do, and the standards body publishes that. I don't mean this as a complaint. It is how most of the platform you rely on got specified, and this is one of the cleanest examples.

A name nobody can fix. The current living standard carries a sentence I find oddly moving: "The name XMLHttpRequest is historical and has no bearing on its functionality." It was true the weekend the thing was written. The XML was a shipping excuse from the start, and the web will carry it for as long as there is a web, capital letters and all.

The synchronous flag outlived its reason. Hopmann's first version "didn't have async support hooked up", so the blocking mode came first and the famous one was added in the rewrite. A blocking request freezes the page while it waits, and browsers have been trying to remove it for years. The spec says synchronous requests outside of workers are "in the process of being removed from the web platform", and then adds, in brackets, "This is a long process that takes many years." A blocking mode from a weekend prototype is still being negotiated a quarter of a century later.

The engine in the diagram became the framework. Garrett's essay describes the browser loading "an Ajax engine", written in JavaScript, that is "responsible for both rendering the interface the user sees and communicating with the server on the user's behalf". In 2005 that was a box in a figure. It is also a fair description of what a single-page application framework does, written years before the big ones existed. The problems arrived with it. Garrett's Q&A lists, as open questions, accessibility, the back button, and what happens when JavaScript is off, and answers all of them with "maybe". The industry spent the next fifteen years turning those maybes into routers, history APIs and server rendering.

The security review came later. The rule browsers settled on was that a page could call only its own server, and the 2006 draft gives it one line: "Same-origin security restrictions SHOULD apply." Everything developers then wanted, calling other people's servers, needed a new permission system, which is where the 2008 Level 2 draft's "cross-site requests" and the CORS errors in your console come from. The "quick security review" of the late 1990s has been followed by a rather longer one.

The replacement, fetch, arrived in the mid-2010s, and MDN describes it as "a more powerful and flexible replacement for XMLHttpRequest". It returns a promise instead of counting to 4. The old constructor is still in every browser, and a great deal of code still calls it through one wrapper or another.

The takeaway

The capability and the name are different inventions, and the web needed both. Microsoft shipped the capability in 1999, for one product, under a name chosen to get it past a release deadline. It worked. Hardly anyone outside noticed, because it was locked to one browser, because the industry was in a slump, because the best examples were hidden behind logins and paywalls, and because nobody could say in a meeting what it was. Each of those took years to clear, and the last one was cleared in an afternoon's reading by a designer who had written no part of the code.

I'd argue that makes Garrett's essay a piece of engineering in its own right. Hopmann, who built the first version, came to the same view: "effective marketing and communication of your ideas is important and we missed out on that." A feature that can't be named can't be asked for, budgeted, taught or put in a job ad. The object had one name that was wrong from its first day and survived anyway; the technique had none for six years and stayed obscure until it got one.

What I couldn't verify

  • Almost everything about how XMLHTTP was written and shipped rests on one account, Alex Hopmann's. He gives no date for the weekend, the naming or the security review beyond starting the webmail work "probably sometime in late 1998", and his page shows no original publication date.
  • Jesse James Garrett's essay is linked as a saved copy of its print view, because Adaptive Path's own site would not load.
  • The dates for Mozilla, Safari 1.2 and Opera 8.0 support come from Wikipedia, as do Oddpost's 2002 opening and the release months of Internet Explorer 5 and 7. Wikipedia's XMLHttpRequest article also dates the idea to 2000, which contradicts Hopmann; I followed Hopmann.
  • Jay Hoffmann's history of the web says XMLHTTP was added to replace Java components that Outlook Web Access had relied on. Hopmann does not mention this, so I left it out.
  • How little the object was used before 2004 is hard to measure. Aaron Swartz wrote that nobody he knew used it, but Hopmann says the approach was already doing well by 2000 to 2002, and it was common on corporate intranets.
  • Google's two blog posts are linked for their dates only. Whether Google Maps used XMLHttpRequest or hidden frames at launch is disputed in the comments on Swartz's post, so the essay does not say.
  • That XMLHTTP sitting behind ActiveX held back public sites, that Prototype's wrapper kept most developers from typing the constructor, and that the missing name mattered as much as I say, are my own readings.
