getYear() and the year 19100

13 min read

A method that was right, got fixed, got fixed back, and is still shipping in the browser you are reading this in.

var now = new Date();
"19" + now.getYear();  // "19100"

Through the late 1990s, lines like that one printed the year in page footers and "last updated" stamps, and they were correct every time anyone checked. In 1998 it said 1998. In 1999 it said 1999. On the first morning of 2000 it said 19100, unless the visitor's browser was one of the ones where it said 192000.

The usual Y2K story is about two-digit years stored in old mainframe records to save space. This one is different, and I think more useful to a working developer. getYear() never stored two digits. It returned a perfectly unambiguous number, the documentation said what the number was, and the trouble came from three separate attempts to make it nicer. By January 2000 the same call gave different answers in browsers from the same vendor, and the standard had already given up on it.

Before: years since 1900

The convention is older than the web. C's struct tm, the structure that localtime() fills in, has a member called tm_year, and the POSIX definition of <time.h> describes it in three words: "Years since 1900." The neighbouring member, tm_mon, is the month of the year from 0 to 11. If both of those look familiar, it is because you have been living with them in JavaScript for thirty years.

They got there by way of Java. Java 1.0 shipped a class called java.util.Date with a getYear() that returned the year minus 1900 and a getMonth() that counted from zero. JavaScript took the whole thing. Allen Wirfs-Brock and Brendan Eich, in their history paper "JavaScript: The First 20 Years", put it bluntly: "JavaScript 1.0 Date was a direct transliteration, bugs and all, of the java.util.Date class of Java 1.0." The list of inherited details they give includes "externally numbering months from 0–11, and Year 2000 ambiguities that were present in the Java design." The reason, they write, was "Java interoperability requirements."

Eich has been less formal about it elsewhere. In 2003 Eric Lippert, who worked on Microsoft's JScript, wrote a post about JavaScript's date oddities and wondered aloud why months start at zero. The post preserves Eich's reply: "My answer: because that's how java.util.Date did it." JavaScript was under orders to be Java's little brother, and the team was "trying not to reinvent wheels to be any more or less round than Java's equivalent." Then the line that covers today's topic: "Unfortunately, java.util.Date had a pile of y2k and usability bugs."

So Navigator 2 shipped a getYear() that returned the year minus 1900. For 1996 that is 96. It looks exactly like a two-digit year, which is the whole problem. A number that happens to look like "the last two digits" for the first few years of a language's life will be used as the last two digits, whatever the manual says.

Three fixes and a standard

Here is the sequence, as well as the surviving sources let me reconstruct it.

1996: Netscape fixes it. Navigator 3 changed the method. Danny Goodman, explaining in 1998 why the calendar examples in the JavaScript Bible were about to break, described the change: "getYear() started its life returning the year value as the year minus 1900. But starting with Navigator 3, the method returned a four-digit year for years starting with 2000." The new rule was 96 for 1996, 99 for 1999, then 2000 for 2000. My best guess at the reasoning is that somebody looked at 100 and saw a Y2K bug waiting to be reported. That same year, Microsoft's first JScript shipped in Internet Explorer 3 with the original behaviour. Microsoft's archived JScript reference still records it: for JScript 1.0, "the year 1899 is returned as -1 and the year 2000 is returned as 100."

1997: Microsoft fixes it the same way, and Java walks away. Internet Explorer 4 adopted the Navigator 3 rule. The same Microsoft page gives the examples: "1996 is returned as 96, but 1825 and 2025 are returned as-is." Lippert's version, from inside the building, is that the original IE implementation was the mistake: "Fortunately we corrected that incompatibility in the second version." Meanwhile the method's source had disowned it. JDK 1.1, in February 1997, deprecated java.util.Date's year, month and day methods in favour of a new Calendar class. The Java 8 documentation for getYear() still opens with the word "Deprecated."

June 1997: the standard writes down the original. The first edition of ECMA-262 had to say what getYear does, and with the browsers disagreeing, it picked the oldest answer. Section 15.9.5.5 ends in one step: "Return YearFromTime(LocalTime(t)) − 1900." It also carries an apology in advance: "This function is specified here for backwards compatibility only. The function getFullYear is much to be preferred for nearly all purposes, because it avoids the 'year 2000 problem.'" That sentence was published two and a half years before the year 2000.

August 1998: Netscape un-fixes it. Navigator 4.06 shipped JavaScript 1.3 with a claim of ECMA-262 compliance, and compliance meant going back to year minus 1900. Phil Schwartau, handling a bug report for Mozilla in July 2000, relayed the developers' account in a Bugzilla comment: "Between JavaScript versions 1.2 and 1.3, we rewrote the Javascript Date object from the ground up." The new code followed the draft standard. The resulting behaviour "was different from many (but not all) JavaScript Date implementations, but we retained it to be compliant with the evolving standard."

December 1999: the standard gives up. The third edition of ECMA-262, approved on December 16, 1999, moved getYear out of the main text and into Annex B, the appendix for things implementations may keep for old pages' sake. Schwartau's account covers Netscape's dilemma at that point. They had just changed the method to match a standard that no longer required it. "Rather than revert to the old getYear behavior and force scriptwriters to be aware of yet another version difference, we decided to keep the year - 1900 behavior for getYear, and encourage the use of getFullYear." And then, with admirable restraint: "It's not an ideal situation, but that's the history."

Put it all in one place and this is what a script could expect on New Year's Day:

// new Date(2000, 0, 1).getYear()
// Navigator 2, IE 3         100
// Navigator 3              2000
// IE 4 and IE 5            2000
// Navigator 4.06 and up     100
// ECMA-262                  100

Then the day came. The mainframes mostly held. The web got a rash of cosmetic damage, and not only from JavaScript, since Perl's localtime and Java's getYear() followed the same C convention. Wikipedia's account of the day lists the US Naval Observatory, keeper of the country's official time, giving the date on its website as 1 Jan 19100. Météo-France showed a forecast map dated 01/01/19100. Al Gore's presidential campaign site briefly announced that it was 3 January 19100.

On that same January 3, two things were published. On irt.org, Martin Webb posted "JavaScript Y2K Issues", a careful field guide to the mess. And at 23:39 UTC someone opened Mozilla bug 22964, "JavaScript: getYear returns '100' for 2000." Two hours and twenty minutes later John Morrison closed it as invalid: "this behaviour is as designed and documented."

Why a one-line method went so wrong

It would be easy to file this under carelessness. I don't think that's fair to anyone involved. Each decision had a defensible reason behind it, and the reasons pulled in different directions.

A marketing mandate picked the API. Nobody at Netscape sat down and designed a year accessor that returned 95. They were told the language had to sit alongside Java and script its applets, so the date object matched Java's method for method. Java had copied the shape of C's time structure. The convention arrived in your browser third-hand, and each hand assumed the previous one had thought about it.

The original design was correct, and that made it fragile. Raymond Chen made this point in the comments on Lippert's post. The C convention "was actually good and correct," he wrote: "if you paid close attention and always added 1900 to the year, you always got the right answer." The catch is "if you paid close attention." For five years the wrong mental model, that this was a two-digit year, produced right answers. An API that rewards the wrong model until a known future date is a trap, however accurate the documentation.

The fix destroyed information. Chen again, on the Navigator 3 and IE 4 rule: "if you called getYear and got 80 back, you could never be sure whether that was the year 80 or the year 1980." Year minus 1900 is reversible. The friendlier rule is a two-digit year with an escape hatch, and it broke the one thing the old method was good for, which was subtracting one year from another. A script that computed someone's age as this year minus birth year would get 2000 minus 65.

Following the standard was a moving target. Netscape did what developers always say they want vendors to do. It tracked the draft spec, even where that meant changing shipped behaviour. Then the committee demoted the method, and Netscape was left holding a behaviour change it had made for the sake of a requirement that no longer existed. Microsoft ignored the standard on this point and stayed compatible with its own previous release, which from the point of view of an intranet full of IE-only pages was the responsible choice.

Nobody could remove anything. By 1997 the method was known to be a hazard, a replacement existed, and the spec said so in writing. It stayed, because pages were already calling it and a browser that breaks existing pages loses to the browser that doesn't. Hold that thought for the last section.

How everyone coped

The obvious answer was getFullYear(), which the version 4 browsers and the standard had added for exactly this purpose. The obvious answer was not available. As Webb put it, "so long as there are people using Netscape Navigator 2 and 3 and Internet Explorer 3, there will always be a need to use getYear(), as these browsers obviously do not support getFullYear()." So the era's solution was to keep calling the broken method and launder the result.

Webb's version is the tidiest:

function y2k(number) { return (number < 1000) ? number + 1900 : number; }

If the browser gave you a small number, it meant years since 1900. If it gave you a big one, it was already a year. Goodman's patch for the book's calendars, dated 16 September 1998 in its own comment, was the same idea with the threshold at 1900 and the name get4DigitYear. Both carry the cost Chen described. Webb's cannot represent a year before 1000 and Goodman's cannot represent one before 1900, because the function can no longer tell 80 from 1980. For a page footer, nobody minded.

Peter-Paul Koch's QuirksMode went further. The page introduced the problem with "Netscape devised a complex solution that even Netscape itself doesn't completely follow," noted that "Netscape 3 (and only 3) follows Explorer," and then recommended throwing away everything except the last two digits and rebuilding the century from scratch:

function takeYear(theDate) {
  x = theDate.getYear();
  var y = x % 100;
  y += (y < 38) ? 2000 : 1900;
  return y;
}

Why 38? "Because Epoch Time will end in 2038." That is a Y2K workaround whose expiry date is the next date bug on the calendar, written down cheerfully and on purpose. I find it hard not to admire.

My favourite coping strategy is in the report that opened that same Mozilla bug in July 2000. The reporter's own code handled the year like this:

// javascript .getYear() isn't Y2K compliant
datedisplay.setAttribute("value", dateObj.getDate()+"/"+(dateObj.getMonth()+1)+"/"+(2100-dateObj.getYear())+" "+hour+":"+minutes);

In 2000, getYear() returns 100, and 2100 minus 100 is 2000. In 2001 it returns 101, and the page announces that it is 1999. That fix was good for exactly twelve months, and to be fair, it was written in one of them.

What it left behind

The bug report became the documentation. Bug 22964 was closed in two hours and then refused to stay quiet. It has 67 duplicates. The last was filed in July 2013. Of its 80 comments, 51 date from 2005, which I'd guess is what happens when a browser built on that engine starts taking real market share and meets a web tested only in Internet Explorer. The thread contains the entire standards-versus-reality argument in miniature. One commenter quotes Annex B and concludes: "Mozilla should behave as it behaves now, and IE is wrong." Another answers with the point that browser vendors eventually organised their whole philosophy around: "the Mozilla user who browses the Internet CANNOT use getFullYear instead of getYear because he is not the author of the page he is browsing!!!" Both were right. The author of the page and the person hurt by the page are different people, and only one of them can deploy a fix.

The standard won, more than a decade late. The reference page on WebPlatform.org records the end of the split: "In Internet Explorer 3.0, and then in Internet Explorer versions starting with Internet Explorer 9 standards mode, the value returned is the stored year minus 1900." So for the year 2000, Internet Explorer's answer went 100, then 2000 from IE 4 through IE 8, then 100 again. A page that had relied on the middle answer for a decade would break on upgrade, in the name of interoperability. And the change applied only in IE9's standards mode, so the older document modes went on giving the old answer. The fix for the fix for the fix came with a switch.

Annex B is a museum that charges no admission and never closes. Wirfs-Brock and Eich describe what the committee thought it was doing in 1999 by moving "the non-Y2K compliant Date methods" to an annex: the hope was that it "would signal that these were deprecated features, which should not be used and that implementations were empowered to eventually remove them." Their verdict: "This was a naïve expectation." Browser makers would not remove anything a page might use, because "some Web pages never go away." Today's Annex B has stopped pretending. It says its contents "are required when the ECMAScript host is a web browser," and that every feature in it has "one or more undesirable characteristics and in the absence of legacy usage would be removed from this specification." The Y2K warning from 1997 is still there, nearly word for word. So is the method. I ran new Date().getYear() in a current Chromium build while writing this and got 126.

The replacement took thirty years. Temporal, the new date and time API, is now at Stage 4 at TC39, and its README opens with a sentence nobody will dispute: "Date has been a long-standing pain point in ECMAScript." MDN describes it as "designed as a full replacement for the Date object," and is unsentimental about the original: "the Date API is based on the poorly designed java.util.Date class from Java." In Temporal a date's year is the year and January is month 1. MDN also still flags it as limited availability, not yet in every major browser. And notice the form the fix takes. Temporal is a new global object sitting beside Date. It replaces nothing, because nothing can be replaced. Java reached the same arrangement decades earlier: its getYear() was deprecated in 1997 and was still in the API documentation, deprecation notice attached, as of Java 8.

There is a pattern in that list that I think goes beyond dates. Every change made to getYear() in place broke somebody's working page: Netscape's in 1996, Microsoft's in 1997, Netscape's again in 1998, Microsoft's again with IE9. The only move that helped was the one that left the old method alone and added getFullYear() next to it. Later this turned into a slogan: don't break the web. The people who wrote the 1997 standard were already learning it the hard way, from a function with one line of arithmetic in it.

The takeaway

The original getYear() was never wrong. It returned years since 1900, as documented, in Navigator 2, and it returns that today. What failed was everything around it: a borrowed design that looked like something it wasn't, two vendors fixing it in place at different times, and a standard that arrived after the fixes and sided with the original. The lesson I'd take is that once an API is on the web, changing what it returns is the most expensive thing you can do to it, and it stays expensive even when the change is an improvement. Add the new thing beside it, mark the old one as legacy, and accept that you will be shipping both for the rest of your career.

Which, if you started in the 1990s, you have been. The line at the top of this essay still runs. It prints 19126 this year, in any browser that follows the specification. Somewhere there is probably a page where it does.
